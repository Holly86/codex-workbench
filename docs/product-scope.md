# Product scope

## Product statement

Codex Workbench will be a self-hosted, browser-based, single-user interface for official OpenAI
Codex app-server operation against Git repositories below /workspace/repositories. It is a
Workbench client, not an OpenAI-compatible API facade and not a replacement implementation of
Codex.

## Users and trust

The initial product has one administrator/user. “Single-user” describes account cardinality, not a
trusted network. Every browser is untrusted until it owns an authenticated Workbench session.
Repository contents, Codex authentication state, uploads, app-server events, and approvals are
server-side assets.

## Foundation scope

This phase establishes durable boundaries:

- architecture, security model, deployment model, ADRs, and staged roadmap;
- Codex CLI 0.146.0 protocol schemas generated by the official local generator;
- FastAPI application, environment configuration, structured logs, health probes, safe path
  resolution, direct-child transport contract, and constrained repository discovery;
- responsive and accessible React shell with connection state and prepared interaction regions;
- non-root container definitions, internal backend, public frontend gateway, persistent mounts,
  healthchecks, and initialization scripts;
- automated tests, linting, typing, frontend build, and repository checks.

App-server startup is disabled and no privileged browser API is exposed in this phase. This is a
security property, not an unfinished bypass.

## Planned product capabilities

Later phases may add authenticated sessions, repository selection, thread creation/resume,
streamed turn and item events, visible tool activity, approvals, interruption, paste and
drag-and-drop uploads, true localImage input, file context, and then Git status/diff, a file
browser, Monaco Editor, and xterm.js.

## Explicitly out of scope now

- complete chat or production app-server lifecycle;
- production Codex-thread or approval UI;
- terminal, editor, Git commit or push;
- multi-user administration;
- public internet exposure or domain-specific reverse-proxy configuration;
- deployment, container restart, GitHub creation, commit, or push;
- unofficial APIs, Chat Completions emulation, or Open WebUI reuse.

## Success criteria

The phase succeeds when the documented architecture can evolve without replacing its security and
transport boundaries, generated schemas match Codex 0.146.0, both applications build, local checks
pass, Compose is statically coherent, and unavailable host capabilities are explicitly reported.

## Open product decisions

- final product name and visual identity;
- retention periods for uploads, audit metadata, and expired sessions;
- whether nested repositories beyond direct children should be discovered;
- default sandbox and approval policy choices after user testing;
- license selection;
- exact reverse proxy and HTTPS termination on the target NAS.
