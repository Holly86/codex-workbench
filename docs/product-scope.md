# Product scope

## Product statement

Codex Workbench will be a self-hosted, browser-based, single-user interface for official OpenAI
Codex app-server operation against Git repositories below /workspace/repositories. It is a
Workbench client, not an OpenAI-compatible API facade and not a replacement implementation of
Codex.

## Users and trust

The initial product has one administrator/user. “Single-user” describes account cardinality, not a
trusted network. Every browser is untrusted until it owns an authenticated Workbench session.
Repository contents, Codex authentication state, uploads, app-server events, and approvals are
server-side assets.

## Implemented scope

The architecture/foundation and authenticated-boundary phases establish durable boundaries:

- architecture, security model, deployment model, ADRs, and staged roadmap;
- Codex CLI 0.146.0 protocol schemas generated by the official local generator;
- FastAPI application, environment configuration, structured logs, health probes, safe path
  resolution, direct-child transport contract, and constrained repository discovery;
- productive one-time single-user setup, Argon2id verifier, server-side sessions, CSRF/Origin
  enforcement, login rate limiting, and authenticated WebSocket handshake;
- responsive and accessible authentication states and protected React shell;
- normalized protocol-independent domain models plus a Codex 0.146.0 capability matrix for
  permissions, events, usage, rate limits, approvals, and image inputs;
- non-root container definitions, internal backend, public frontend gateway, persistent mounts,
  healthchecks, and initialization scripts;
- automated tests, linting, typing, frontend build, and repository checks.

App-server startup remains disabled. Authentication routes are productive, while no repository,
thread, turn, upload, approval, tool, command, or shell browser API is exposed. This is a security
property, not an unfinished bypass.

## Planned product capabilities

The next phase may add the managed app-server, repository/thread selection, explicit permissions,
streamed turn and item events, visible activity, approvals, usage/rate limits, interruption,
reconnect, paste and drag-and-drop uploads, and true localImage input. Later phases may add file
context, Git status/diff, a file browser, Monaco Editor, and xterm.js.

## Explicitly out of scope now

- productive app-server lifecycle or Codex turn;
- production Codex-thread or approval UI;
- terminal, editor, Git commit or push;
- multi-user administration;
- password recovery/change and multi-user administration;
- public internet exposure or domain-specific reverse-proxy configuration;
- deployment, container restart, GitHub creation, commit, or push;
- unofficial APIs, Chat Completions emulation, or Open WebUI reuse.

## Success criteria

The current phase succeeds when all non-public APIs fail closed without a valid session, all HTTP
mutations require Origin and CSRF, the UI exposes the complete authentication lifecycle, generated
schemas match Codex 0.146.0, capability claims have exact evidence, both applications build, and
all locally available checks pass.

## Open product decisions

- final product name and visual identity;
- retention periods for uploads, audit metadata, and expired sessions;
- password recovery and password-change operator workflow;
- whether nested repositories beyond direct children should be discovered;
- final non-elevated sandbox and approval defaults after runtime probing and user testing;
- license selection;
- exact reverse proxy and HTTPS termination on the target NAS.
