  ## Root Cause

  npm install --global @openai/codex@0.146.0 erzeugt:

  /usr/local/bin/codex
    -> ../lib/node_modules/@openai/codex/bin/codex.js

  Der bisherige Einzeldatei-Copy:

  COPY --from=codex-cli /usr/local/bin/codex /usr/local/bin/codex

  folgte diesem Symlink. In der Runtime entstand dadurch eine reguläre Kopie von codex.js unter /usr/local/bin/codex, nicht der ursprüngliche Symlink.

  Der Launcher ermittelt sein Paket relativ zu seinem eigenen realen Pfad. Am falschen Ort suchte er deshalb unter /usr/local/vendor/... statt im kopierten npm-Paket. Das native Paket

  @openai/codex-linux-x64/
    vendor/x86_64-unknown-linux-musl/

  war vorhanden, konnte vom verlagerten Launcher aber nicht aufgelöst werden. Dieses Verhalten folgt direkt aus dem versionsgenauen Codex-0.146.0-Launcher
  (https://github.com/openai/codex/blob/rust-v0.146.0/codex-cli/bin/codex.js) und der Multi-Stage-Copy-Semantik von BuildKit.

  Konkret schlug daher dieser Teil fehl:

  version_output="$(/usr/local/bin/codex --version 2>&1)"

  Der Launcher beendete sich mit Exit 1. Da stderr durch 2>&1 in version_output verschwand, zeigte Docker keine Codex-Fehlermeldung. Der nachfolgende test und codex app-server --help wurden
  nicht mehr ausgeführt.

  Nur die Runtime-Stage war betroffen, weil die Node-Stage noch den originalen npm-Symlink am korrekten Ort besaß.

  Zusätzlich wurde ein latentes zweites Problem beseitigt: Die kopierte offizielle Node-Runtime benötigt libstdc++6; Systempakete einer Build-Stage werden durch COPY --from nicht in eine
  andere Basis übernommen. Die finale Python-Slim-Stage installiert diese Library jetzt explizit. Das offizielle Node-Slim-Image ermittelt seine notwendigen Runtime-Pakete ebenfalls anhand
  der dynamischen Abhängigkeiten des Node-Binaries (Node-Dockerfile (https://github.com/nodejs/docker-node/blob/main/24/bookworm-slim/Dockerfile)).
